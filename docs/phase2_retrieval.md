# 第二阶段设计说明：BM25 + 向量混合检索

> 目标：把第一阶段切出来的 **7507 条 chunk（10 家公司）** 建成可检索的索引，
> 实现 BM25、向量、以及两路融合三种召回方式，**每条结果都能追溯到原始年报页码**。
>
> 这一阶段**只做召回，不生成任何文字**，也**没有接任何大模型**。
> 返回的每条结果都挂着一个完整的 `Chunk`，公司名 / 页码 / 章节直接来自
> `data/chunks` 的原始记录，检索过程不参与文本生成，所以引用不会失真。

---

## 一、整体流程

```
data/chunks/*.jsonl  (7507 条)
        │
        ├─► scripts/build_index.py ──┬─► index/bm25/     倒排索引 + 文档长度
        │                            └─► index/vector/   7507×512 float32 + norms
        │
        └─► src/retriever.py ──► search(query, mode=bm25|vector|hybrid)
                                    │
                                    ├─ 1. 从 query 里识别公司（别名表）
                                    ├─ 2. 按公司建**布尔掩码**（打分前过滤）
                                    ├─ 3. 各路召回 → 融合（RRF）
                                    └─ 4. 挂回原始 Chunk → citation()
```

索引只需建一次：

```bash
python scripts/build_index.py             # 增量：chunks 没变就跳过
python scripts/build_index.py --check     # 只看指纹，不重建
python scripts/build_index.py --force     # 强制重建
```

命令行检索：

```bash
python -m src.cli search "中国平安2025年归属于母公司股东的净利润是多少？" -k 5
python -m src.cli search "太保的资产规模" --mode bm25 --show-text 200
python -m src.cli search "比较平安和国寿的净利润" --mode hybrid
```

## 二、四个关键设计决策

### 1. BM25 自己实现，没有用 `rank-bm25`

`src/bm25.py`，Okapi BM25，`K1=1.5`、`B=0.75`、
`idf(t) = ln(1 + (N - df + 0.5) / (df + 0.5))`。

不用现成库的原因很具体：**需要在打分前按公司做布尔过滤**。
通用库算完分再让调用方筛，会有很实际的损失 —— 问"中国平安的总资产"，
top-10 里可能 8 条是中国人寿的段落，筛完只剩 2 条，等于白召回。
自己实现就能把掩码直接压进打分的循环里：

```python
for doc_idx in postings[term]:
    if allowed is not None and not allowed[doc_idx]:
        continue          # 不是这家公司的，分数根本不算
```

### 2. 简繁归一 —— 本阶段影响最大的一处修正

**10 家公司里有 5 家是港股年报**（中国人保、中国太平、中国再保险、中国财险、
众安在线），正文是**繁体**。按 chunk 数算：

| | chunk 数 | 占比 |
|---|---|---|
| 繁体正文（5 家港股） | 3937 | **52.4%** |
| 简体正文（5 家 A 股） | 3570 | 47.6% |

不处理的话，简体提问"总资产"永远匹配不上原文的"總資產" —— 这 5 家会像坏掉
一样查不出来。发现它的过程也很直接：q19 和 q20 的 BM25 top-10 **一模一样**，
说明分词结果里根本没有区分度。

解决办法是 `zhconv` 简繁归一，但**只在分词 / 向量化那一层做**，
chunk 原文一个字都不动 —— 否则引用里的原文就变了。

- BM25：`tokenize()` 入口处 `text = to_simplified(text)`，建立索引和查询都走它
- 向量：`build()` 和 `embed_query()` 各自转一次
- 缺 `zhconv` 时**直接报错，不静默跳过**（`src/tokenize.py`）—— 静默跳过会退化成
  "5 家公司查不到"这种极难排查的故障

效果（BM25 目标召回率，两次测量都在同一 b 下对比，不跨设置混着说）：

| | 不做简繁归一 | 做简繁归一 |
|---|---|---|
| b=0.75（旧默认） | 61.3% | 74.2% |
| **b=0.1（现默认）** | **74.2%** | **83.9%** |

简繁归一本身带来约 **+10 个百分点**（74.2% → 83.9%，当前的 b 下实测）。
上面第二节的 b 调整是叠加在这之上的另一项收益，两者互不冲突。

### 3. BM25 的 b 取 0.1，而不是教科书的 0.75

这是本阶段**第二处关键修正**，也是提升最大的一处。

BM25 公式里的 `b` 控制长度归一化的强度：`b=1` 时长文档被罚得最狠，
`b=0` 完全不罚。教科书和几乎所有现成库的默认值都是 `b=0.75`
（在网页 / 新闻语料上调出来的）—— 那种语料里文档越长越"泛"，被罚是合理的。

**但财报 chunk 正相反**：承载答案的往往是长段落或长表格（一页合并资产负债表
能切出几十个数字），而短 chunk 多是目录、页眉、单行小标题。按 0.75 罚长度，
等于专门压制最有信息量的那些 chunk。

实测（29 题、top-10）：

| k1 | b | BM25 命中 | BM25 目标召回 | 混合命中 | 混合目标召回 | 混合 MRR |
|---|---|---|---|---|---|---|
| 1.5 | **0.75（旧默认）** | 21/29 | 74.2% | 24/29 | 83.9% | 0.519 |
| 1.2 | 0.75 | 21/29 | 74.2% | 23/29 | 80.6% | 0.520 |
| 1.2 | 0.4 | 23/29 | 80.6% | 25/29 | 87.1% | 0.600 |
| 1.2 | 0.3 | 23/29 | 80.6% | 25/29 | 87.1% | 0.596 |
| 1.2 | 0.2 | 23/29 | 80.6% | 24/29 | 83.9% | 0.613 |
| **1.2** | **0.1（现默认）** | **24/29** | **83.9%** | **26/29** | **90.3%** | **0.633** |
| 1.2 | 0.0 | 24/29 | 83.9% | 26/29 | 90.3% | 0.632 |

**这里要如实说明白，不要把数据说得比它本身更整齐**：低 b 区间内部并不是
单调的 —— 混合命中数按 b=0.0/0.1/0.2/0.3/0.4 排是 26、26、24、25、25，
b=0.2 处有个凹坑。**这个 ±1 道题的抖动就是 29 道题的噪声底。**

所以真正站得住的结论只有一条：**b≈0.1 明显好于 b=0.75，而不是
"在 0.0/0.1/0.2 里挑出了最优的那个"。** 后者是在噪声上做选择。
取 0.1 而不是 0.0，是想保留一点长度归一化而不是彻底关掉 ——
两者实测打平，没有理由把这项机制整个砍掉。

**为什么说"低 b 更好"不是在这批题上调出来的假象：**

1. **方向在三个独立的 k1 上都一致**：k1 取 1.2 / 1.5 / 2.0，b≈0.0~0.1
   都是各自最好的一档，b=0.75 都是最差的一档。三个设置给出同一个方向。
2. **对半交叉验证**：把 29 题分成两折，在一折上选 b、到另一折上验，
   b≈0.1 **两个方向都赢**，b=0.75 两个方向都是最差或并列最差。
3. **对比是粗粒度的**：我比的是 0.75 与 0.1 这两档（差距 3 道题 / MRR 0.11），
   不是在低 b 区间里精挑细选 —— 后者会过拟合。
4. **机制说得通，而且预测对了会修好哪些题**：是在诊断"中国太保 / 中国太平的
   总资产"时先发现这两条长 chunk 在 **BM25 自己的排名里**被罚到了第 8、第 9
   （见第三节），才去动 b 的。调完之后这两条升到第 **1**、第 **4** 名，
   两道题都从失败变成命中 —— 先有机制假设、后有结果，不是反过来去凑。

```
折 A 调参 → 折 B 留出：  b=0.1 → 13/14 (93.3%)    b=0.75 → 11/14 (80.0%)
折 B 调参 → 折 A 留出：  b=0.1 → 13/15 (87.5%)    b=0.75 → 12/15 (81.2%)
```

> ⚠️ 改 `K1` / `B` 常量后**必须重建索引**（`python scripts/build_index.py --force`）。
> `BM25Index` 整个对象被 pickle，`k1`/`b` 会跟着存进索引文件；`load()` 里已经
> 强制用代码里的常量覆盖掉文件里的旧值，避免"改了参数却毫无效果"这种难查的问题。

### 4. 多公司问题按公司分组召回

问"比较平安和国寿的净利润"，如果直接全库取 top-10，正文长、反复提该指标的
那一家会把名额占满，另一家一条都进不来 —— 实测这道题三路都只召回了一半。

所以默认 `multi_company="per_company"`：**每家公司各召回 top_k 条，再按排名
跨公司融合**。要的答案是"两家分别是多少"，不是"其中一家是多少"。

## 三、融合：为什么用 RRF，以及一次失败的优化

RRF（Reciprocal Rank Fusion），`k=60`：

```
score(d) = Σ_r  weight_r / (k + rank_r(d))
```

选它是因为**只看名次、不看原始分数**，对量纲免疫 —— BM25 分数无上界，
余弦在 [-1,1]，直接加权相加必须先校准，而 min-max / z-score 没有一个是稳的。

### 融合配置实测对比（29 题，top-10；在 b=0.1 之下做的）

| 配置 | 题目命中率 | 目标召回率 | MRR | 失败题 |
|---|---|---|---|---|
| **rrf pool=50 1:1（默认）** | **26/29** | **90.3%** | 0.633 | q13 q20 q29 |
| union pool=50 | 26/29 | 90.3% | 0.634 | q13 q20 q29 |
| union pool=50 2:1 | 25/29 | 87.1% | 0.580 | q05 q13 q20 q29 |
| weighted pool=50 | 25/29 | 87.1% | 0.641 | q13 q20 q28 q29 |
| rrf pool=50 2:1 | 24/29 | 83.9% | 0.575 | q05 q13 q20 q28 q29 |
| rrf pool=50 3:1 | 24/29 | 83.9% | 0.564 | q05 q13 q20 q28 q29 |
| rrf pool=10 1:1 | 24/29 | 83.9% | 0.570 | q09 q13 q20 q28 q29 |
| rrf pool=50 1:2 | 23/29 | 80.7% | 0.583 | q11 q13 q18 q20 q28 q29 |

复现：`python scripts/eval_retrieval.py --sweep`

**结论：融合方式调不出差别，rrf 与 union 并列最好。**
`rrf 1:1` 和 `union` 的 26/29、MRR 0.633/0.634 是同一档；加权和缩小 pool 都更差。
`weighted` 的 MRR（0.641）名义上最高，但命中少一道 —— 它把正确答案往前挪的
同时也把别的挤掉了，不值得为此换一个对分数量纲更敏感的方法。

所以默认取**最简单、最好解释**的那个：`rrf`、`pool=50`、权重 1:1。
调参调到这个份上还分不出高下，说明瓶颈不在融合方式。

### 一次失败的优化：先修错了地方

早期（b 还是 0.75 时）有两道题是"BM25 单独能召回、混合反而召不回"：

- q11「中国太保2025年末的总资产」：BM25 排第 8
- q18「中国太平2025年末的总资产」：BM25 排第 9

当时的解释是 RRF 的池子被稀释：这两条只有 BM25 一路召回，拿的是 `1/(60+8)`；
向量一路在 pool=50 里贡献了几十条候补，每条 `1/(60+r)`（r<8）都比它高，
于是被挤出 top-10。这个机制描述**没错**，但它只是**近因**。

针对它试了两版融合改造，都没用：

1. **`union_fuse`**（`src/hybrid.py`）：把候选集限制成两路前 top_k 的并集。
   没用 —— 竞争那一路的前 8 名**仍然在候选集里**，照样压在上面。
2. **每路留固定席位**（quota fusion）：让每路的前 `quota` 名无条件进结果。
   同样没救回来，而且 `quota≥4` 会把 rrf 本来答对的 q09/q10/q15 弄丢。
   根子在于"保底席位"等于把 BM25 的前 8 名原样塞进结果，混合退化成 BM25。

**真正的原因不在融合层**：是 `b=0.75` 把这两条长 chunk 在 **BM25 自己的排名里**
就压到了第 8、第 9。把 b 降到 0.1 之后它们升到第 **1**、第 **4** 名，
融合再怎么稀释也丢不掉 —— 两道题都变成命中。

**教训**：混合检索出问题，先看单路各自的排名，再怀疑融合。
当时如果先把 BM25 的 top-10 打出来看一眼，就不会花两轮去改融合。

`union_fuse` 保留在 `src/hybrid.py` 里并附了实测结论，是为了让上面这张表可复现；
**默认不用它**（现在与 rrf 打平，没有采用的理由）。quota 那版实现已经删除 ——
它的 docstring 声称的保证它并没有真正做到（保底进来的条目会按 RRF 重排后被
截掉），留着比删掉更危险。

## 四、评测方法

题目在 `configs/eval_questions.yaml`：**29 道，覆盖全部 10 家公司**，
分三类 —— `exact`（精确，23）、`semantic`（语义，4）、`cross`（跨公司，2）。

打分规则（`scripts/eval_retrieval.py`）：

- **命中 = 公司 + 页码同时对上**。只比页码不够 —— 中国人保和中国财险的页码
  会撞车（两份年报都几百页），只比页码会把两家的答案算成同一个。
- 每道题的每个 target 有一个 `pages` **列表**，收录所有载有该数字的页。

  > 这一点是踩过坑才改的：第一版只标了"我第一次翻到的那一页"，结果把
  > BM25 实测命中率从 52% 压到了 41% —— 模型召回的是**另一页上的同一个数字**，
  > 标注却只认一页。改法是全篇扫描"数字 + 指标关键词"同时出现的页。

- MRR 用首个正确结果的排名；未命中的题按 0 计。
- Top-1 命中是最苛刻的一档：决定答案能不能直接引用第一条，还是得人工往下翻。

## 五、最终评测结果（29 题，top-10）

| 检索方式 | 题目命中率 | 目标召回率 | MRR | Top-1 命中 |
|---|---|---|---|---|
| BM25 | 24/29 (82.8%) | 83.9% | 0.535 | 11/29 |
| 向量 | 19/29 (65.5%) | 64.5% | 0.273 | 3/29 |
| **混合** | **26/29 (89.7%)** | **90.3%** | **0.633** | **14/29** |
| 公司识别 | **29/29 = 100%** | | | |

按题型：

| 题型 | 题数 | BM25 | 向量 | 混合 |
|---|---|---|---|---|
| 精确 | 23 | 21/23 (91%) | 15/23 (65%) | 22/23 (96%) |
| 语义 | 4 | 1/4 (25%) | 3/4 (75%) | 3/4 (75%) |
| 跨公司 | 2 | 2/2 (100%) | 1/2 (50%) | 1/2 (50%) |

**两路的分工在数据上很干净**：

- **精确题**（含数字、科目名）BM25 91% vs 向量 65% —— 关键词匹配的主场
- **语义题**（不含数字的转述问法）BM25 1/4，向量 3/4 —— 向量的主场

这正是做混合检索的理由：两路的强项不重叠，融合才拿到 90.3%。

不过要如实说清楚混合的收益有多大：

- **精确题上混合确实比任一单路都好**：22/23，而 BM25 是 21/23、向量 15/23。
  融合把 BM25 漏掉的 1 道补了回来，同时没丢掉 BM25 答对的那些。
- **语义题和跨公司题上，混合只是追平了较好的那一路**（语义 3/4 = 向量，
  跨公司 1/2 = 向量），没有额外收益；跨公司题甚至还不如 BM25 单独（2/2，
  见第六节 q29）。

所以混合的整体领先（26/29 对 24/29、19/29）主要来自精确题，
外加"不用预先知道该用哪一路"这个工程上的好处。

> 混合 Top-1 命中 14/29 意味着：**将近一半的问题，第一条结果就是正确来源**，
> 可以直接引用；其余的需要往下翻几条。

完整逐题明细（每道题三路各召回了哪些 chunk、公司、页码、章节）：
`docs/qa/retrieval_eval.json`（逐题）、`docs/qa/retrieval_eval.md`（汇总表）。

## 六、已知局限（如实记录，未修）

混合检索最终剩 3 道不中（q13、q20、q29）：

1. **q13「太保的资产规模有多大」三路全败**。问法里没有任何指标关键词
   （既没有"总资产"也没有数字），BM25 无从下手，向量也没能把它和
   "总资产"这一概念对上。属于真正困难的转述，不是索引缺陷。
2. **q20「中国再保险2025年的总保费收入」**。gold chunk
   （`china_re_2025_annual_p0021_c0036`，671 字 UTF-8、317 个词）确实存在，
   正文里就写着"實現總保費收入人民幣1,803.68億元"。把 b 降到 0.1 之后它在
   china_re 内部的 BM25 排名从第 119 名升到**第 30 名**（得分 16.79，
   第一名 22.84），仍是进不了 top-10。原因是这条长段落里"保费"只出现 1 次、
   "收入"2 次，而该公司短 chunk 里这两个词反复出现，tf 优势压过了长文档。
   属于 BM25 词频模型的固有短板，不是 b 没调好。
3. **q29「比较中国太保和新华保险2025年末的总资产规模」混合 1/2，反而比
   BM25 单独（2/2）差**。太保那半丢了：太保的 gold（p33）在 BM25 那一路只排到
   第 7，而向量那一路在太保里一条 gold 都没有 —— 两家交错融合后太保只剩
   5 个名额，全被向量那 5 条挤掉。和前面 q11 当初的现象同型，只是这道题的
   gold 名次更靠后（第 7 对第 1），降 b 也救不回来。

未修的取舍：这几条都是**真实存在的困难**，不是索引 bug。其中 q20 要修得动
BM25 的词频假设（比如换 BM25+ 或加字段权重），属于另一个量级的改动；
q13 要真正的语义匹配进步（换更大的向量模型）。

另外两个第一阶段遗留、与本阶段无关的问题：

4. **新中华人寿 p295 有 1 条 chunk 分词为 0 词**（`..._p0295_c0738`，
   24 个字符的乱码）。原因是该页 PDF 缺 ToUnicode 字体映射，抽取出来就是乱码。
   仅 1 条，保留未删。索引统计里"最短 0 词"就是它。
5. **港股 6 家的 `section` 字段只能当参考**（页眉驱动的章节归属没做），
   详见 `docs/qa/README.md`。这不影响检索 —— 召回用的是正文，
   但引用里显示的章节名可能不对。

## 八、一个必须做的安全检查

索引里的 `doc_idx` 是个**整数下标**。一旦索引与 chunks 的顺序或内容对不上，
检索会拿着**正确的分数指向错误的 chunk** —— 表现为"答案看着对、页码是错的"，
是所有失败模式里最难发现的一种。

所以 `Retriever.load()` 每次都跑 `verify_consistency()`：索引里的 `doc_ids`
必须与 chunks **完全同序**，否则直接抛错并提示重建索引。
`build_index.py` 另外用 chunks 指纹（`chunk_id + text` 的 sha256）判断索引
是否过期。这两道检查都有对应的单元测试（含"条数相同但顺序不同"这种最隐蔽的情况）。
